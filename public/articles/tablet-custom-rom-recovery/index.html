Recovering a 2015 Galaxy Tab A 9.7 LTE: how to debug a failed custom ROM and return to stock

This guide records one recovery attempt on a Samsung Galaxy Tab A 9.7 LTE (model SM-T555, codename gt510lte). The tablet had been running an unofficial LineageOS 18.1 build, and a series of failed installs left it unable to start. It was then restored to the Samsung stock firmware. The guide sets out how the faults were diagnosed, which checks separated a bad file from a bad link, and which method finally worked. The steps were run from a Raspberry Pi, although a Manjaro laptop was available as a fallback. The guide is organised as follows: what to prepare, how to identify the device, how to check files and links, and how to restore stock firmware.

What you need

  • The tablet, a charger and two USB data cables, one of which must be known to carry data.
  • A computer running Linux, with adb, heimdall, unzip, sha256sum and md5sum.
  • The firmware or ROM file, downloaded from a source you trust, with its published checksum.
  • Time. A sideload of an 850 MB file took between 15 and 25 minutes, and a Heimdall flash of the stock partitions took about 15 minutes.

Step 1: identify the device before anything else

The codename decides which build is safe to install, because a zip built for another model can brick the device. It is therefore the first thing to confirm.

adb shell getprop ro.product.device
adb shell getprop ro.build.version.release

On this tablet the codename was gt510lte and the release was 11. Keep the serial number and IMEI out of any public post.

Step 2: check the file before the transfer

Checksums come first, because a bad file and a bad link produce the same symptom on the tablet. To tell them apart, the checks run in this order.

  1. Compare the file size with the published value.
  2. Compare the SHA256 or MD5 with the published value. Where the project publishes no checksum, record the size and the hash, and treat the test as a completeness check only.
  3. Run an integrity test on the archive:
unzip -tq file.zip

The output must read No errors detected. A zip with no end-of-central-directory record was produced by a download that stopped early. This happened once here, after a resumed download that ended at 892,633,088 bytes. The file looked complete by size, but the archive was not readable.

The check that matters most is the one made on the copy you will send. Repeat the hash on the computer after every copy, because the copy can be damaged on its way to the device. Only a file that passes all three checks should go to the tablet.

Step 3: read the recovery messages, not the progress bar

Recovery logs the install in order. Read each line before you choose anything.

Message on screen What it means What to do
E:footer is wrong The zip failed its signature footer. The file is damaged or unsigned. Stop. Do not tap Install anyway.
Signature verification failed. Install anyway? The same failure, offered as a choice. Tap No.
E:failed to verify whole-file signature The archive does not match its signature. Stop. Re-download and re-check.
E:error: 21 or status 2 / status 3 The updater script aborted. Stop. Read the full log before retrying.
adb: failed to read command: Success (on the computer) The link dropped during the transfer. Check the link before you retry.
Install completed followed by a boot loop The install ran, but the result is not usable. Restore from a known-good image.

A line such as script succeeded: result was [1.000000] shows that the script ran. It does not, however, show that the system is bootable. In this session the script reported success for two installs, and both returned to recovery at the first reboot. The status line is therefore a necessary result, not a sufficient one.

Step 4: separate a bad link from a bad file

Several sideloads stopped between 44% and 47%, with the same error. The Pi's copy of the file passed its hash check each time, so the file on the computer was not the cause. The tablet side is the next suspect.

Check the link while the transfer runs:

adb devices -l
sudo dmesg | grep -i 'usb' | tail

The state sideload means the device is ready. The states offline and unauthorized mean the link has not completed its handshake. A USB disconnect line in the kernel log, during a transfer, confirms that the cable or port dropped out.

Three actions were tried in this session. Replugging the cable at the tablet end, with the tablet kept on the sideload screen, often cleared the offline state. Changing the cable was followed by a transfer that reached the install stage, although one cable does not prove the cause. The logs alone cannot separate a cable fault from a connector fault, so this guide does not claim a root cause.

Do not resume a partial transfer. In this session the resumed download was not used for the install, so each attempt should start from a fresh, fully checked file.

Step 5: stop when the tablet will not boot

A boot loop after a sideload means the system partition is damaged or inconsistent. Repeating the sideload usually makes the damage worse, so the method must change. In this session the tablet went back to recovery three times after an install reported success.

The reliable way out was a full image restore, not another sideload. Samsung tablets have a separate flash mode, Download mode, which Heimdall can write to. Heimdall writes each partition directly, so it does not depend on the recovery menu or on an ADB session.

Step 6: restore the stock firmware with Heimdall

Samsung's firmware is a set of images inside tar archives, each with a trailing MD5. Verify each archive before you flash it.

  1. Verify the package. For each .tar.md5 file, the last line holds the expected hash. The hash covers every byte before that line. Compute the hash of the file without the trailer and compare. In this session three of four packages matched. The modem package did not, so it was not flashed.
  2. Extract the archives:
tar -xf BL_*.tar.md5
tar -xf AP_*.tar.md5
tar -xf CSC_*.tar.md5
  1. Read the partition table to check the partition names:
heimdall print-pit --file GT510LTE_EUR_OPEN.pit

  1. Put the tablet in Download mode. Hold Volume Down, Home and Power until a warning screen appears, then press Volume Up.

  2. Check that the computer sees the tablet:

heimdall detect
  1. Flash the partitions. Use the names from the PIT file. A name that is not in the table stops the whole session before anything is written:
heimdall flash --SBL1 sbl1.mbn --ABOOT aboot.mbn --RPM rpm.mbn \
  --QSEE tz.mbn --QHEE hyp.mbn --BOOT boot.img --RECOVERY recovery.img \
  --SYSTEM system.img.ext4 --CACHE cache.img.ext4 \
  --HIDDEN hidden.img.ext4 --USERDATA userdata.img.ext4 \
  --PERSIST persist.img.ext4 --no-reboot

Heimdall v2.1.0 has no reboot subcommand. A flash session ends by rebooting the device, so the tablet leaves Download mode once the session closes.

Step 7: when Download mode will not release

After the flash, the tablet stayed in Download mode with the message "Downloading… Do not turn off target". A long press of the Power button did not change that. The working fix was to reconnect the cable and open a new Heimdall session. The session wrote one partition again, from a verified image, and then ended with Rebooting device. The tablet then left Download mode and started the stock first boot.

Use this method only with a verified image. Writing an unverified image in this state repeats the risk of the original install, and it removes the chance to correct the mistake before the tablet reboots.

Pitfalls

  • The Google package and the ROM must match. An Android 11 Google package does not install on an Android 13 ROM. Check the release notes for both.
  • Do not trust a package name alone. A MindTheGapps arm64 package fails on a 32-bit device. This tablet runs armeabi-v7a only.
  • A failed install can still change the system partition. Recovery may format /system before it reports the error. Check the state of every partition before the next attempt.
  • The modem image is a separate risk. Skipping it gave a booting stock system here. Mobile calls on the restored system are not yet tested.

Limits

This guide does not argue that the method works for every unit. Rather, it claims that the checks above separated a bad file from a bad link on one tablet. The checks come from one tablet, and another unit can behave differently. - The archives were checked against published values from third-party sites. The original vendor's signature was not verified. - The modem image was skipped, so this guide does not cover mobile calls or data. - Stock Android 7.1.1 has no security updates. Use it on a trusted home network only.

Summary and conclusion

The recovery succeeded after the method changed. Stock firmware written through Heimdall restored a bootable system, whereas three custom ROM installs failed or boot-looped. The main findings are that the file was rarely the fault, that the transfer link was the most likely failure point, and that recovery messages must be read in full before any retry. Taken together, these points suggest that a verified image written in flash mode is the safest route back for a damaged device.

Rules I would keep

  1. Identify the device by codename before you copy anything to it.
  2. Check the file on the computer that will send it, after every copy.
  3. Read each recovery message, and stop on any signature or footer error.
  4. Do not resume a partial transfer.
  5. When an install returns to recovery, change the method. Do not repeat the same install.
