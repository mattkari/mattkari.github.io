Three Claude Code Sessions, One Orchestrator, One Auditor: My Day-to-Day AI Workflow as a Test Automation Engineer

Matt Karimov · Test automation engineer · October 2026

How I run Karate API and Playwright UI automation in parallel Claude Code sessions, let a third session orchestrate them, compile what each one learns into a shared wiki at the end of the day, and keep Microsoft Copilot as the auditor above it all.

Why I'm writing this down

On a normal day I work on two automation frameworks at once: a Karate suite for APIs and a Playwright suite for the UI. For a long time my AI help was one chat window and one coding assistant, and I spent half my effort re-explaining context.

Then, in one working day, I found a setup that holds context for each workstream separately, lets the sessions coordinate, and leaves a written record of what was learned. This article is that full process: the tools, the two "second brains" behind it, the three-session workflow, and the end-of-day loop that ties it together.

It is one engineer's setup, tested over its first full working day. Treat it as a pattern to adapt, not a product.

1. Current AI tooling setup

I have three AI tools available at work, and each earned a different job:

  • Microsoft Copilot: my primary chatbot and auditor. Copilot supports several models, including other vendors' thinking models, but I run it with Claude models. I don't use it for agentic coding. Its strength is that it's integrated with work email, Confluence, OneDrive and OneNote through built-in retrieval (RAG). It can search across everything I have access to, so it already behaves like a "second brain" for organisational knowledge.
  • GitLab Duo: coding assistance in IntelliJ and VS Code. It's hooked into both IDEs. In practice I found it less efficient than Copilot for day-to-day questions, so it's no longer my first choice.
  • Claude Code: my daily tool for agentic coding. This is the tool that reads the repo, runs commands, edits files and iterates, and it's what made the workflow below possible.

The split matters: Copilot knows the organisation; Claude Code knows the code. Neither replaces the other.

2. Second-brain architecture: two brains, two jobs

The Copilot brain (organisational knowledge)

  • OneNote: one section per project (Karate, Playwright), holding notes, decisions and how-tos.
  • Confluence: wiki pages written with deliberate keywords, so Copilot's search finds them as context.
  • Copilot memory: set up with my working preferences, so I don't repeat them in every chat.

This brain is about finding things: a decision from last month, a page someone else wrote, an email thread.

The Claude Code brain (Karpathy-style markdown files)

Following Andrej Karpathy's idea that at personal scale an LLM reading well-kept markdown beats a search database (I set out a fuller version of this in an earlier article: Karimov, 2026c), Claude Code gets two plain files:

  • skills.md: how I work and how to do recurring tasks (conventions, commands, the "right way" in each framework).
  • learnings.md: what we discovered: fixes, gotchas, flaky-test causes, repeatable actions.

Both are loaded into context at the start of every new session, so a fresh Claude Code session starts knowing what yesterday's session learned.

Before Claude Code

Before Claude Code, I ran all my "agentic" work through Copilot by having it generate PowerShell commands that I executed myself. It worked, but I was the loop: copy, run, paste back. Amazon Bedrock with Claude Code wasn't available to me at work, so Claude Code became the agentic layer.

3. The multi-session Claude Code workflow (today's discovery)

The three sessions

I run three Claude Code sessions in parallel, each in the tool that suits its workstream:

# Where it runs Role Workstream
1 Standalone PowerShell window Orchestrator; also builds the second brain Coordination + wiki
2 PowerShell terminal inside VS Code Independent coder, API specialist Karate API automation framework
3 PowerShell terminal inside IntelliJ Independent coder, UI specialist Playwright UI automation (183 test cases automated to date)

All three are PowerShell. The difference is where they live: the two specialists run in the integrated terminal of the IDE that suits their framework, so the code, the test runner and the agent share one window.

Each session has its own context window, but the two frameworks are not walled off from each other. They test the same system from two sides, and they stay in sync on purpose.

The Playwright suite isn't "UI only". It works with the real API traffic underneath the browser, using the patterns from my article Testing the Screen and the Services Behind It (Karimov, 2026a), which is based on my Playwright Java real API traffic guide (Karimov, 2026b): waitForResponse to pair each UI action with the call it triggers, and a background network recorder that logs every request for diagnostics. I mainly use three ways of working:

  1. Seed via API, validate via UI. Create the test data through the API (for example, a test record), then check the UI shows it correctly. A two-phase wait first polls the same search endpoint the grid uses, so a failure tells you whether the data or the UI broke (Karimov, 2026a, use case 4).
  2. Trigger via UI, capture the API call. Click through the real UI flow and capture the request and response it fires: the server-generated ID, the payload contract, the status code (Karimov, 2026a, use cases 1, 2 and 8).
  3. Seed via UI, validate via the UI flow. Create the data through the screens themselves and follow it through the end-to-end journey, the way a user would, closing with a reload check that catches an optimistic update that never saved (Karimov, 2026a, use case 5).

This is why the two sessions belong together. The Karate session knows the API contracts in depth. The Playwright session sees how the UI calls those microservices, and the network and routing logic behind each screen. Between them I understand how the UI integrates with the services underneath, which neither framework shows on its own.

So the sessions are independent but learning from each other. Each works in its own repo and its own context, and what one discovers reaches the other through the shared wiki. When Karate maps a new endpoint, the Playwright session can use it to seed data. When Playwright captures an unexpected call or status code, the Karate session can turn it into an API test.

I don't think of the two specialist sessions as junior assistants. Each is an independent coder that specialises in one area: it plans, writes, runs and fixes its own work inside its lane. The orchestrator coordinates them; it doesn't do their thinking for them.

Choosing the model per task

Every session plans on the strongest model and codes on the cheapest model that can do the job:

  • Claude Opus 5.5 for planning: breaking down a feature, designing a test strategy, deciding how a change fits the framework.
  • Claude Sonnet 5.5 for most coding: implementing tests, refactoring, debugging failures.
  • Claude Haiku 5.5 for simple, repetitive work: small edits, boilerplate, renames, quick lookups.

I switch per task, not per day. Planning on a weaker model produces plans that fall apart halfway; coding everything on the strongest model wastes budget on work a smaller model does just as well.

How the sessions talk to each other

Separate context windows don't mean separate islands. The sessions communicate via PowerShell commands: the orchestrator session passes instructions across to the other two, and they report back through files on disk.

The rule that keeps this safe: one writer per file. Each worker session writes only its own notes; only the orchestrator writes the compiled wiki. Three agents writing to the same file is a merge conflict between agents, and it's worse than one between people.

End-of-day knowledge capture flow

This loop turns a busy day into something I keep:

  1. Karate session (VS Code): asked to summarise the day's learnings and extract repeatable actions into a markdown file.
  2. Orchestrator (PowerShell): instructs the VS Code session to save that file into the raw/ directory.
  3. Playwright session (IntelliJ): does the same for the UI automation learnings, into raw/.
  4. Orchestrator: compiles all the raw files into a single wiki.
   VS Code (Karate) ──summary.md──┐
                                  ├──► raw/ ──► Orchestrator compiles ──► wiki/
IntelliJ (Playwright) ─summary.md─┘                (PowerShell session)
                                                        │
              every session can query the wiki ◄────────┘

After compiling, the second brain can be queried from all sessions. Tomorrow's Playwright session can ask which endpoint today's Karate session used to create a test record, seed its data through that endpoint, and check the result in the UI. The answer comes from the wiki, not from my memory.

This is the Karpathy pattern in practice: raw/ is the source, the compile step is the build, and the wiki is the artefact. As a QA engineer I think of it like a build pipeline: notes go in, a tested, linked knowledge base comes out.

The supervision model: auditor, orchestrator, specialists

  • Microsoft Copilot, running Claude Opus, is the auditor. It has the most context of anything in the setup, because its built-in RAG reaches Confluence, OneNote, OneDrive and email. I take plans and finished work to it and ask whether they fit how things are actually done here. It checks; it doesn't build.
  • The standalone PowerShell session is the orchestrator. It passes instructions to the two specialists and owns the wiki.
  • The VS Code and IntelliJ sessions are independent specialists. Each owns its framework end to end.

The auditor's role may not be permanent. Copilot audits well today because it can see organisational knowledge the Claude Code sessions can't. As the compiled wiki grows and gets richer, more of that context will live in files every session can read, and I may retire Copilot from the auditor seat. The wiki is slowly replacing the reason the auditor exists.

And above all of them: me. Merges, pushes and anything irreversible stay with the human.

4. Rules that make it work

  • One workstream per session, shared knowledge. Each session owns its own framework and repo; they meet in the wiki, not in each other's code.
  • One writer per artefact. Workers write their own raw notes; only the orchestrator writes the wiki.
  • Summaries are claims; diffs and test runs are evidence. When a session says "all tests pass", check the run.
  • Capture before you close. The end-of-day summary is the step that makes tomorrow faster. Skip it and the day's learning dies with the context window.
  • Keep the MD files clean. No credentials, no client data, no production details. Learnings stay at technique level, such as "wait for the dashboard locator after SSO", never anything that identifies a system or a customer.
  • The human presses merge. Agents propose; I approve.

5. Honest limitations

  • One day of evidence. The three-session pattern held up across a full working day, morning to evening. That is a promising start, not a long-term result.
  • The auditor depends on Copilot's RAG. Until the wiki holds that organisational context, removing Copilot would remove the widest view in the setup.
  • Coordination is still partly manual. The orchestrator passes instructions, but I'm still deciding when each step happens.
  • Shared memory is only what's written down. If a learning isn't in raw/ or the wiki, the other sessions don't know it.
  • Token cost multiplies. Three sessions each read their own context. It pays off on full-day work, not on a quick fix.
  • Policy comes first. Use only tools your organisation has approved, on its accounts, and check what may go into notes before you start.

6. Key takeaways

  • Separate Claude Code sessions each have their own context window, but they can still communicate. The orchestrator passes instructions, and files on disk carry the results.
  • Copilot (with Claude models) acts as the auditor, because its RAG gives it the most context; the Claude Code sessions are independent specialists, with one session acting as orchestrator.
  • Plan on Opus, code on Sonnet or Haiku. Pick the model per task, not per day.
  • Multi-session orchestration enables parallel workstreams with shared knowledge output. API and UI automation progress side by side and feed one wiki.
  • The frameworks are independent but learn from each other. Playwright seeds via API, triggers via UI and captures the calls, while Karate goes deep on the contracts, so together they show how the UI integrates with the microservices underneath.
  • The end-of-day compile is the multiplier. Each session's learnings become every session's starting context the next morning.
  • It held up across a full working day, morning to evening. Next I'll run it for a few weeks and report back on what breaks.
