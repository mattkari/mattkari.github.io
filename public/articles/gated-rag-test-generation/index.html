Two Gates and a Rule: Building a Review-Only RAG Pipeline That Drafts API and UI Tests

Dusmamat (Matt) Karimov · 30 October 2026 · 13 min read

All system, service, endpoint, ticket and field names in this article, its screenshots and its diagram are illustrative placeholders. The screenshots are mock-ups that reproduce the layout of the tool, not captures of it.

Why I built it

Writing test cases for an API is rarely difficult. Finding everything a good test case depends on is the hard part. The requirement sits in one story, the acceptance criteria in another, the design in a wiki page, the contract in an OpenAPI file, the routing rules in a gateway repository, and the existing tests in a third repository. A language model can draft test cases in seconds, but only from what it is given. If the evidence is incomplete, the draft is confident and wrong.

This article describes the pipeline I built to deal with that problem: a retrieval-augmented (RAG) test assistant that gathers the evidence first, shows it to a person twice, and only then asks a model to draft candidate tests. Today I moved its flow onto LangGraph, and the first real end-to-end run completed. The article explains the design, the rules behind it, and what I found while building it.

It should be noted at the outset that this is not a tool that writes tests for you. Rather, it is a tool that prepares evidence and drafts candidates for an engineer to review. Nothing it produces is published anywhere.

The design in one sentence

Gather evidence deterministically, let a human approve it twice, block generation when anything is missing, and keep everything the model saw.

In other words, the model is the smallest part of the system. It is called once, at step 9 of 11. The other ten steps exist to decide whether it should be called at all.

The sources: local, read-only, pinned

The pipeline reads from four places (Figure 1, top row):

  1. The issue tracker and the wiki, through an Atlassian MCP server.
  2. Source repositories, through a GitLab MCP server: the gateway, the service under test (here, "Service A") and the existing automated tests.
  3. The OpenAPI contract for the target operation.
  4. A hosted language model, through an approved enterprise endpoint.

Both MCP servers run locally in Docker containers. MCP (Model Context Protocol) is a standard way for an AI application to call tools; here the tools are "get this story", "get this page" and "read this file". Running the servers locally means the pipeline talks to containers on my own machine rather than to a third-party integration, and I control exactly which tools are exposed. Both are used read-only.

Three rules govern the sources:

  • Explicit wiki pages only. The pipeline retrieves the page IDs it is given. It does not search the whole wiki and guess.
  • Committed content only. Every file is read from committed content at a named reference (for example HEAD), never from uncommitted local changes. The limit is stated honestly: freshness is unverified, because the pipeline does not fetch, so the local reference may be behind the remote.
  • An anchor match is a relevance signal, not proof of sufficiency. Finding the endpoint path in a wiki page tells you the page is relevant. It does not tell you the page contains enough to test it.

The flow: eleven steps, two gates

LangGraph lets me express the pipeline as a fixed graph of steps instead of a free-roaming agent. The order is deterministic: the same request walks the same path every time.

  1. Load the request and validate it against a schema.
  2. Preflight: check inputs and configuration, and show a summary (target, repositories, limits).
  3. Gate 1: a person approves the scope, or the run stops.
  4. Check that the live MCP clients respond. (In "fakes" mode, used for offline tests, this step is skipped and no model is called.)
  5. Acquire evidence: stories, wiki pages, the contract with every $ref resolved, the gateway's routing and validation, the controller and its call chain, and the existing tests.
  6. Build the evidence pack: remove duplicates, fix the order, enforce size and item limits, and record what was truncated.
  7. Gate 2: a person reviews the evidence, its size and its limitations, or the run stops.
  8. Check sufficiency: every required item must be present.
  9. Generate: the model drafts candidate tests from the exact prompt measured before Gate 2.
  10. Write the outputs.
  11. End.

A request is a small JSON payload (schema version 1.1). An API request looks like this, with every value a placeholder:

{
  "schemaVersion": "1.1",
  "qaStoryKey": "PROJ-102",
  "baStoryKey": "PROJ-103",
  "featureKey": "PROJ-101",
  "workItemType": "API",
  "sourceMode": "LIVE",
  "reviewOnly": true,
  "target": {
    "method": "PATCH",
    "path": "/api/records/{recordId}/items"
  },
  "confluencePageIds": ["100000001"],
  "repositorySelection": {
    "mode": "EXPLICIT",
    "repositories": [
      {
        "role": "API_AUTOMATION",
        "root": "C:/projects/api-tests",
        "contentMode": "COMMITTED",
        "reference": "HEAD",
        "searchPaths": [
          "api-tests/src/test/resources/features/records/item-update.feature"
        ]
      }
    ]
  },
  "candidateLimits": {
    "coreRequired": 5,
    "recommendedRiskBased": 0,
    "optionalExploratory": 0,
    "maximumTotal": 5
  }
}

A UI request uses the same shape without a target, because a UI change has no single endpoint:

{
  "schemaVersion": "1.1",
  "qaStoryKey": "PROJ-202",
  "baStoryKey": "PROJ-203",
  "featureKey": "PROJ-201",
  "workItemType": "UI",
  "sourceMode": "LIVE",
  "reviewOnly": true,
  "repositorySelection": {
    "mode": "EXPLICIT",
    "repositories": [
      {
        "role": "UI_AUTOMATION",
        "root": "C:/projects/ui-tests",
        "contentMode": "COMMITTED",
        "reference": "HEAD",
        "searchPaths": [
          "ui-tests/src/test/resources/features/records/view-toggle-ui.feature"
        ]
      }
    ]
  },
  "candidateLimits": {
    "coreRequired": 5,
    "recommendedRiskBased": 0,
    "optionalExploratory": 0,
    "maximumTotal": 5
  }
}

Four fields carry most of the safety:

  1. reviewOnly: true keeps every output as a draft for a person.
  2. repositorySelection.mode: "EXPLICIT" with searchPaths limits the repository search to named feature files, so the scope stays focused and existing-test evidence cannot flood the pack.
  3. contentMode: "COMMITTED" with reference: "HEAD" reads committed content only, never uncommitted changes in a working copy.
  4. candidateLimits caps how many candidates of each tier the model may return. The values above are the ones the first runs used; the risk tier at 0 is one of the limits discussed later.

One small habit has also proved useful. When a story key has not been verified yet, the request carries an obvious placeholder such as <QA_STORY_KEY> instead of a plausible key. A placeholder fails validation at step 1; a wrong but valid key would quietly pull evidence from an unrelated task.

The rule that does the most work: missing evidence blocks generation

For API work, the pipeline will not generate until all six items are present:

  1. The feature, BA and QA stories.
  2. At least one design page with relevant anchors.
  3. The contract: target operation found and every $ref resolved.
  4. The gateway's routing and validation configuration.
  5. The controller and its call chain.
  6. A completed, bounded search of the existing tests.

If the contract cannot be interpreted, for example because of a circular or broken $ref, the run blocks. There is deliberately no fallback to "send the raw operation and hope". To put it simply, a model that is not given the contract will invent one, and the invented version will look plausible.

Budget control: measure the prompt before anyone approves it

The exact prompt is built once, before Gate 2, so the person approving the evidence is approving what the model will actually see. Generation reuses that same prompt text; it is not rebuilt afterwards. A hard cap on prompt size applies: if the cap is missing or exceeded, the run blocks. The prompt's SHA-256 hash is written with the outputs, so any candidate can be traced to the exact prompt that produced it.

The token count is currently an estimate (characters divided by four). The diagram labels it as uncalibrated, because structured text such as YAML and JSON usually tokenises less efficiently than prose, so the estimate can under-count.

The outputs

Each run writes a folder of five files:

File Purpose
candidate-tests.json the drafted candidates, machine-readable
candidate-review.md the same candidates, laid out for a human reviewer
coverage-summary.md what the candidates cover, against the evidence
open-questions.md what the model could not determine from the evidence
generation-manifest.json the run record, including the prompt hash

The open-questions file is, interestingly, the most useful of the five. It shows where the evidence ran out, which is usually where a conversation with the business analyst or developer should start. The next section explains why.

A local web page (/graph) drives all of this: a form or JSON input, presets, an interactive view of the graph, panels for both gates, and artefact download.

Open questions as a BA-ready agenda

The first real run produced five candidate tests and, alongside them, a list of open questions. Each question sits under the candidate test it blocks. The questions fell into a small number of recurring kinds. Illustrative versions, with placeholder field names, look like this:

  • Field mapping: "Which response field maps to the business term Category, and is the mapping one-to-one?"
  • Derived values: "Should each amount field in the response equal the stored value, or a value derived from it (for example a calculated total)?"
  • Timing: "When should startDate be populated in this response, and in what format?"
  • Interacting flags: "How do the item-level includeInTotal flag and the record-level includeInTotal flag relate, and which one wins?"
  • Contract facts: "What HTTP status code does the documented success response use?"

In other words, the model separated what it could test from what only a person can decide, and it wrote the second part as questions a business analyst can answer. This changes the value of the pipeline. It drafts test candidates, but it also prepares the requirements conversation, and it does so before any test exists, which is when gaps in requirements are cheapest to fix.

Three practices make the BA meeting efficient:

  1. Group the questions by topic (status codes, field mapping, dates, flags) rather than by test, so one answer can unblock several candidates.
  2. Mark each question as either answerable from a document or needing a decision. The first kind should have come from the evidence, not from the BA.
  3. Record each answer in the story's acceptance criteria. The next run then finds the answer as evidence instead of asking the same question again.

The second practice matters more than it first appears. A question such as "what is the success status code?" is not a business decision; the OpenAPI contract answers it. When a contract fact reaches the BA as an open question, it is a signal that the contract did not reach the model. That signal led to the most important finding below.

What I found while building it

Building the pipeline was also a review of it. Four findings are worth recording.

First, a rejected run is a successful run. One early run was rejected at Gate 1 and wrote nothing. That is the design working: a wrong scope cost one click, not a folder of misleading tests.

Second, the sufficiency gate let a run through without its contract. The design says an unresolved contract blocks generation. Yet in the first real run, the open questions asked for the success status code and whether an OpenAPI definition existed for the endpoint, which are both facts the contract would have supplied. It can therefore be assumed that the contract was either not retrieved or cut from the evidence pack, and that the sufficiency check at step 8 did not enforce the rule. A gate that can be bypassed is the main risk in a design that depends on gates. The fix is twofold: confirm from the run manifest and evidence pack whether a contract item was present or truncated, and add a test proving that a run with no contract stops at step 8. That test must fail on the current code before the fix is accepted.

Third, existing tests can crowd out the requirements. In the same run, 22 of the 26 evidence items were existing automated tests, and only 4 were requirements, design or QA scope. That is roughly 85% of the evidence describing what is already tested. Existing tests are useful context, but they describe what is already tested, not what should be. The planned fix is to pass existing coverage as a compact index (feature and scenario titles) and spend the budget on requirements and design.

Fourth, long design pages get truncated silently unless you record it. A very long wiki page can lose most of its content to a per-item size limit. Because the evidence pack records truncation, the loss was visible at Gate 2 rather than hidden in a weak output. The better fix is to split long pages into sections and keep the sections that mention the target operation.

Limits

This article does not claim the pipeline produces good tests. Rather, it claims the pipeline produces reviewable candidates from recorded evidence. Four limits remain:

  1. Quality is not yet measured. The first real run produced five candidates, all in the core category. Whether they are right is a separate question.
  2. The sufficiency gate needs a test of its own, because one run passed it without contract evidence.
  3. The token estimate is uncalibrated.
  4. Repository freshness is unverified, because the pipeline does not fetch.
  5. No negative or risk-focused candidates were requested (the run used 5 core, 0 risk, 0 exploratory). For an API, error and boundary cases are where defects usually hide, so these limits need widening. Interestingly, one core candidate still covered an empty-result case.

Next steps

First, close the gate: prove with a failing-then-passing test that a run without a resolved contract stops at step 8. Second, add the scoring step below.

A twelfth node that scores the output

The missing piece is a step after "Write": compare the candidates with a set of trusted, hand-written tests for the same endpoints, and count how many candidates are correct, how many are wrong, and what was missed. Run that across ten endpoints and the pipeline has a measured result instead of a demonstration. It is the same principle the pipeline already applies to the model: do not trust the summary, check the evidence.

Rules I would keep

  • The model is one step of eleven. Put the effort into the other ten.
  • Two human gates: approve the scope, then approve the evidence.
  • Missing evidence blocks generation. No fallbacks that guess.
  • Measure the prompt before approval, and store its hash with the result.
  • Read committed content at a named reference, and say plainly what is unverified.
  • Use an obvious placeholder for any unverified key, never a plausible guess.
  • Review-only by default: a person decides what becomes a real test.
  • Treat open questions as a BA agenda, and treat a contract fact in that agenda as a bug.
  • Test the gates themselves. A gate nobody has tried to bypass is an assumption.

Summary and conclusion

This article set out to describe a pipeline that drafts API and UI test candidates without trusting the model more than it deserves. The approach is to gather evidence deterministically through local, read-only MCP servers, to place two human gates around that evidence, and to block generation whenever a required item is missing. The main finding so far is that the safety of such a system comes less from the model than from the structure around it: the gates, the sufficiency rule and the recorded evidence. A second finding is that the open questions are as valuable as the candidate tests, because they turn gaps in the requirements into a ready agenda for the business analyst, and, read carefully, they also expose gaps in the pipeline itself. The structure, however, is only as strong as its weakest gate, so the gates must be tested, and the quality of the output still has to be measured. Those are the next steps.

If you build something similar at work, ask your employer first, use only approved tools and model endpoints, and keep real system names, tickets and data out of anything you publish.
