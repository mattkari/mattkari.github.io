Two Gates and a Rule: Building a Review-Only RAG Pipeline That Drafts API and UI Tests

Dusmamat (Matt) Karimov · 30 October 2026 · 20 min read

All system, service, endpoint, ticket and field names in this article, its screenshots and its diagrams are illustrative placeholders. The screenshots are mock-ups that reproduce the layout of the tool, not captures of it.

Updated 1 November 2026: added the tool's graph view (Figure 4) and the next stage, which turns approved candidates into Xray tests in Jira. See "Update: the graph view and the road to Xray".

Why I built it

Writing test cases for an API is rarely difficult. Finding everything a good test case depends on is the hard part. The requirement sits in one story, the acceptance criteria in another, the design in a wiki page, the contract in an OpenAPI file, the routing rules in a gateway repository, and the existing tests in a third repository. A language model can draft test cases in seconds, but only from what it is given. If the evidence is incomplete, the draft is confident and wrong.

This article describes the pipeline I built to deal with that problem: a retrieval-augmented (RAG) test assistant that gathers the evidence first, shows it to a person twice, and only then asks a model to draft candidate tests. Today I moved its flow onto LangGraph, and the first real end-to-end run completed. The article explains the design, the rules behind it, and what I found while building it.

It should be noted at the outset that this is not a tool that writes tests for you. Rather, it is a tool that prepares evidence and drafts candidates for an engineer to review. In the version described here, nothing it produces is published anywhere. The next stage, described in the update below, adds publishing to Xray, but only behind further human approvals.

Related work: what the research already says

I am not the first to generate tests from requirements with an LLM, and two recent industrial studies support the central rule of this design.

APITestGenie (Pereira, Lima and Faria, 2026) generates API integration tests from business requirements and OpenAPI specifications using an LLM with retrieval. On ten real-world APIs, including around 1,000 live endpoints from an automotive partner, it produced valid test scripts for 89% of requirements within three attempts, and some generated tests found real defects. Interestingly, the authors found that the level of detail in the requirements and in the API documentation was one of the main factors deciding success.

RAGTAG (Arora, Herda and Homm, 2024) generates test scenarios from natural-language requirements with retrieval, evaluated by experts at Austrian Post. The experts noted that poor or ambiguous input produces poor output, and that problems in a generated scenario usually point back to problems in the requirements.

In other words, both studies measured, after the fact, that input quality drives output quality. This design turns that observation into a rule applied before the model is called: if the evidence is not there, the model is not asked. It also echoes Meta's TestGen-LLM (Alshahwan et al., 2024), which only recommends generated tests that pass a series of explicit filters. Open-source workflows with human review between generation steps also exist; what is less common is a blocking evidence rule that includes code-level evidence, such as gateway routing and the controller's call chain.

The design in one sentence

Gather evidence deterministically, let a human approve it twice, block generation when anything is missing, and keep everything the model saw.

In other words, the model is the smallest part of the system. It is called once, at step 9 of 11. The other ten steps exist to decide whether it should be called at all.

The sources: local, read-only, pinned

The pipeline reads from four places (Figure 1, top row):

  1. The issue tracker and the wiki, through an Atlassian MCP server.
  2. Source repositories, through a GitLab MCP server: the gateway, the service under test (here, "Service A") and the existing automated tests.
  3. The OpenAPI contract for the target operation.
  4. A hosted language model, through an approved enterprise endpoint.

Both MCP servers run locally in Docker containers. MCP (Model Context Protocol) is a standard way for an AI application to call tools; here the tools are "get this story", "get this page" and "read this file". Running the servers locally means the pipeline talks to containers on my own machine rather than to a third-party integration, and I control exactly which tools are exposed. Both are used read-only.

Three rules govern the sources:

  • Explicit wiki pages only. The pipeline retrieves the page IDs it is given. It does not search the whole wiki and guess.
  • Committed content only. Every file is read from committed content at a named reference (for example HEAD), never from uncommitted local changes. The limit is stated honestly: freshness is unverified, because the pipeline does not fetch, so the local reference may be behind the remote.
  • An anchor match is a relevance signal, not proof of sufficiency. Finding the endpoint path in a wiki page tells you the page is relevant. It does not tell you the page contains enough to test it.

The flow: eleven steps, two gates

LangGraph lets me express the pipeline as a fixed graph of steps instead of a free-roaming agent. The order is deterministic: the same request walks the same path every time.

  1. Load the request and validate it against a schema.
  2. Preflight: check inputs and configuration, and show a summary (target, repositories, limits).
  3. Gate 1: a person approves the scope, or the run stops.
  4. Check that the live MCP clients respond. (In "fakes" mode, used for offline tests, this step is skipped and no model is called.)
  5. Acquire evidence: stories, wiki pages, the contract with every $ref resolved, the gateway's routing and validation, the controller and its call chain, and the existing tests.
  6. Build the evidence pack: remove duplicates, fix the order, enforce size and item limits, and record what was truncated.
  7. Gate 2: a person reviews the evidence, its size and its limitations, or the run stops.
  8. Check sufficiency: every required item must be present.
  9. Generate: the model drafts candidate tests from the exact prompt measured before Gate 2.
  10. Write the outputs.
  11. End.

A request is a small JSON payload (schema version 1.1). An API request looks like this, with every value a placeholder:

{
  "schemaVersion": "1.1",
  "qaStoryKey": "PROJ-102",
  "baStoryKey": "PROJ-103",
  "featureKey": "PROJ-101",
  "workItemType": "API",
  "sourceMode": "LIVE",
  "reviewOnly": true,
  "target": {
    "method": "PATCH",
    "path": "/api/records/{recordId}/items"
  },
  "confluencePageIds": ["100000001"],
  "repositorySelection": {
    "mode": "EXPLICIT",
    "repositories": [
      {
        "role": "API_AUTOMATION",
        "root": "C:/projects/api-tests",
        "contentMode": "COMMITTED",
        "reference": "HEAD",
        "searchPaths": [
          "api-tests/src/test/resources/features/records/item-update.feature"
        ]
      }
    ]
  },
  "candidateLimits": {
    "coreRequired": 5,
    "recommendedRiskBased": 0,
    "optionalExploratory": 0,
    "maximumTotal": 5
  }
}

A UI request uses the same shape without a target, because a UI change has no single endpoint:

{
  "schemaVersion": "1.1",
  "qaStoryKey": "PROJ-202",
  "baStoryKey": "PROJ-203",
  "featureKey": "PROJ-201",
  "workItemType": "UI",
  "sourceMode": "LIVE",
  "reviewOnly": true,
  "repositorySelection": {
    "mode": "EXPLICIT",
    "repositories": [
      {
        "role": "UI_AUTOMATION",
        "root": "C:/projects/ui-tests",
        "contentMode": "COMMITTED",
        "reference": "HEAD",
        "searchPaths": [
          "ui-tests/src/test/resources/features/records/view-toggle-ui.feature"
        ]
      }
    ]
  },
  "candidateLimits": {
    "coreRequired": 5,
    "recommendedRiskBased": 0,
    "optionalExploratory": 0,
    "maximumTotal": 5
  }
}

Four fields carry most of the safety:

  1. reviewOnly: true keeps every output as a draft for a person.
  2. repositorySelection.mode: "EXPLICIT" with searchPaths limits the repository search to named feature files, so the scope stays focused and existing-test evidence cannot flood the pack.
  3. contentMode: "COMMITTED" with reference: "HEAD" reads committed content only, never uncommitted changes in a working copy.
  4. candidateLimits caps how many candidates of each tier the model may return. The values above are the ones the first runs used; the risk tier at 0 is one of the limits discussed later.

One small habit has also proved useful. When a story key has not been verified yet, the request carries an obvious placeholder such as <QA_STORY_KEY> instead of a plausible key. A placeholder fails validation at step 1; a wrong but valid key would quietly pull evidence from an unrelated task.

The rule that does the most work: missing evidence blocks generation

For API work, the pipeline will not generate until all six items are present:

  1. The feature, BA and QA stories.
  2. At least one design page with relevant anchors.
  3. The contract: target operation found and every $ref resolved.
  4. The gateway's routing and validation configuration.
  5. The controller and its call chain.
  6. A completed, bounded search of the existing tests.

If the contract cannot be interpreted, for example because of a circular or broken $ref, the run blocks. There is deliberately no fallback to "send the raw operation and hope". To put it simply, a model that is not given the contract will invent one, and the invented version will look plausible.

Budget control: measure the prompt before anyone approves it

The exact prompt is built once, before Gate 2, so the person approving the evidence is approving what the model will actually see. Generation reuses that same prompt text; it is not rebuilt afterwards. A hard cap on prompt size applies: if the cap is missing or exceeded, the run blocks. The prompt's SHA-256 hash is written with the outputs, so any candidate can be traced to the exact prompt that produced it.

The token count is currently an estimate (characters divided by four). The diagram labels it as uncalibrated, because structured text such as YAML and JSON usually tokenises less efficiently than prose, so the estimate can under-count.

The outputs

Each run writes a folder of five files:

File Purpose
candidate-tests.json the drafted candidates, machine-readable
candidate-review.md the same candidates, laid out for a human reviewer
coverage-summary.md what the candidates cover, against the evidence
open-questions.md what the model could not determine from the evidence
generation-manifest.json the run record, including the prompt hash

The open-questions file is, interestingly, the most useful of the five. It shows where the evidence ran out, which is usually where a conversation with the business analyst or developer should start. The next section explains why.

A local web page (/graph) drives all of this: a form or JSON input, presets, an interactive view of the graph, panels for both gates, and artefact download.

Open questions as a BA-ready agenda

The first real run produced five candidate tests and, alongside them, a list of open questions. Each question sits under the candidate test it blocks. The questions fell into a small number of recurring kinds. Illustrative versions, with placeholder field names, look like this:

  • Field mapping: "Which response field maps to the business term Category, and is the mapping one-to-one?"
  • Derived values: "Should each amount field in the response equal the stored value, or a value derived from it (for example a calculated total)?"
  • Timing: "When should startDate be populated in this response, and in what format?"
  • Interacting flags: "How do the item-level includeInTotal flag and the record-level includeInTotal flag relate, and which one wins?"
  • Contract facts: "What HTTP status code does the documented success response use?"

In other words, the model separated what it could test from what only a person can decide, and it wrote the second part as questions a business analyst can answer. This changes the value of the pipeline. It drafts test candidates, but it also prepares the requirements conversation, and it does so before any test exists, which is when gaps in requirements are cheapest to fix.

Three practices make the BA meeting efficient:

  1. Group the questions by topic (status codes, field mapping, dates, flags) rather than by test, so one answer can unblock several candidates.
  2. Mark each question as either answerable from a document or needing a decision. The first kind should have come from the evidence, not from the BA.
  3. Record each answer in the story's acceptance criteria. The next run then finds the answer as evidence instead of asking the same question again.

The second practice matters more than it first appears. A question such as "what is the success status code?" is not a business decision; the OpenAPI contract answers it. When a contract fact reaches the BA as an open question, it is a signal that something went wrong between the contract and the model. That signal led to the most important open question below.

What I found while building it

Building the pipeline was also a review of it. Four findings are worth recording.

First, a rejected run is a successful run. One early run was rejected at Gate 1 and wrote nothing. That is the design working: a wrong scope cost one click, not a folder of misleading tests.

Second, the open questions asked for facts the contract should have supplied. In the first real run, the model asked for the success status code and whether an OpenAPI definition existed for the endpoint. An API contract normally answers both. This observation has at least three possible explanations, and each needs a different fix:

  1. The contract was not retrieved, and the sufficiency check failed to block the run. Fix: enforce the contract rule at step 8, and add a test proving that a run with no contract stops there. That test must fail on the current code before the fix is accepted.
  2. The contract was retrieved but truncated, or the operation does not document its responses. Fix: check adequacy, not only presence. The retained text must contain the target operation and its responses.
  3. The contract was present and complete, but the model did not use it. Fix: place the target operation's responses explicitly in the prompt, and check candidates against them.

The run manifest and evidence pack record which items were present and whether they were truncated, so the explanations can be told apart by inspection. I have not done that inspection yet, so I treat this as a hypothesis, not a finding. Whichever explanation holds, the lesson is the same: a run that was not blocked is not proof that the evidence was sufficient.

Third, existing tests can crowd out the requirements. In the same run, 22 of the 26 evidence items were existing automated tests, and only 4 were requirements, design or QA scope. That is roughly 85% of the evidence describing what is already tested. Existing tests are useful context, but they describe what is already tested, not what should be. The planned fix is to pass existing coverage as a compact index (feature and scenario titles) and spend the budget on requirements and design.

Fourth, long design pages get truncated silently unless you record it. A very long wiki page can lose most of its content to a per-item size limit. Because the evidence pack records truncation, the loss was visible at Gate 2 rather than hidden in a weak output. The better fix is to split long pages into sections and keep the sections that mention the target operation.

Update: the graph view and the road to Xray

Added 1 November 2026.

Two things have changed since the first version of this article. First, the tool now draws its own graph. Second, the plan has moved beyond review-only drafts: approved candidates will become test cases in Xray, the test management add-on for Jira. This section describes both, and it is explicit about what is built and what is not.

Seeing the graph

The local page now renders the LangGraph flow as a diagram (Figure 4). During a run, each step is coloured as not run, ran, waiting for approval, or ended after a rejection. Solid edges are always taken. Dashed edges are taken only when their label holds.

Figure 4. The generation graph of the review-only version, redrawn from the tool's local graph view with placeholder labels. Dashed edges are conditional: both gates can end the run, and in the offline "fakes" mode the flow skips the live client, the wiki and issue-tracker acquisition, and the sufficiency check.

Drawing the graph turned out to be a review tool in its own right. The code expresses conditional paths as small routing functions, and they are easy to read past. The diagram shows them at a glance. Two dashed edges stand out:

  1. "No client" goes from the live-client check straight to the repositories, skipping the issue tracker and the wiki.
  2. "Approved" in offline mode goes from Gate 2 straight to generation, skipping the sufficiency check.

Both belong to the offline "fakes" mode used for tests, in which no real model is called, so they are the intended path. The point is a different one: a single mode flag is all that separates a safe offline path from an unchecked live one. Two guards follow from that. The sufficiency check should run in every mode, and a test should prove that the offline path can never reach the real model endpoint. In other words, every dashed edge that skips a check deserves a test of its own.

From review-only to Xray: the target flow

The next stage keeps the evidence gates and adds the steps that turn an approved candidate into a real test:

  1. You enter the QA story. The tool finds the feature and BA stories through the issue links, and you select them.
  2. You select the API operation from a list. The tool reads the contract and the code files.
  3. Gate 1: you approve the preflight.
  4. The tool collects the evidence: stories, wiki pages, a compact "contract card" for the operation, the request template and the code.
  5. Gate 2: you approve the evidence and the prompt size.
  6. The tool makes one call to the approved model endpoint. It returns up to five candidates.
  7. Code checks each candidate: the method, the path and the field names must match the contract.
  8. Candidate gate: you approve or reject each candidate.
  9. Type gate: you choose Manual or Cucumber.
  10. The tool builds the Xray payload and looks for a duplicate test.
  11. Create gate: you approve. The tool creates the Xray test, then reads it back.
  12. Link gate: you approve. The tool links the test to the BA story, then reads both issues back.

Three safety rules apply to the whole flow: the tool writes nothing to Jira without your approval; the access token is not stored, logged or shown; and if any check fails, the tool stops and deletes nothing.

Four changes in this flow are worth explaining:

  • Choosing instead of typing. Story keys come from the issue links, and the operation comes from a list read from the contract. This removes most of the wrong-key risk that the placeholder habit described earlier was guarding against.
  • Named code files, with caps. The request can now name specific code files. Each file is capped at 20 KB, and an oversized file is skipped with a named warning rather than silently cut. A total cap of 120 KB (about 30,000 estimated tokens) applies across all named files. It should be noted that this is a ceiling, not a target: a typical read scenario needs only about 24 to 26 KB, and the cap exists so that code cannot crowd out the requirements, as existing tests did in the first run.
  • Code checks the model before a person does. Step 7 rejects any candidate whose method, path or field names do not exist in the contract. This is the same principle as Meta's filters (Alshahwan et al., 2024): mechanical checks first, human judgement second.
  • Every write has a gate and a read-back. Creating the test and linking it are separate approvals, and each is confirmed by reading the issues back from Jira rather than trusting the response of the write call.

Status

The new parts are being built in small, separately reviewed changes. The named-file sources, for example, came with 45 new tests, and deliberately breaking the code in seven different ways made the suite fail seven times out of seven. The graph view is working. The remaining steps (the operation list, the request form, the candidate checks and the Xray create and link) are in progress. Nothing has been written to Jira yet; one real create-and-link run is the final step of the plan.

Three open design questions

  1. How many human gates are too many? The target flow has six. Each extra approval adds a chance that people start clicking "approve" without reading. One option is to fold the type choice into the candidate gate (approve as Manual, approve as Cucumber, or reject), and to merge create and link into one publish gate that shows the payload and the link target together. That would leave four.
  2. What happens on a partial failure? If the create succeeds and the link fails, a naive re-run creates a duplicate test. A fingerprint label on each test (run identifier, method, path and scenario) would let the duplicate check find it, and a re-run could resume at the link step.
  3. Can the candidate gate measure quality? If each approve or reject decision is recorded with a reason (wrong field, duplicate, out of scope, missing evidence), the gate produces an adoption rate and a list of failure types as a side effect of normal use. That is the measurement this article has so far lacked.

Limits

This article does not claim the pipeline produces good tests. Rather, it claims the pipeline produces reviewable candidates from recorded evidence. Six limits remain:

  1. Quality is not yet measured. The first real run produced five candidates, all in the core category. Whether they are right is a separate question.
  2. The sufficiency gate needs a test of its own. One run reached generation while asking questions its contract should have answered; the cause is not yet confirmed (see above).
  3. The token estimate is uncalibrated.
  4. Repository freshness is unverified, because the pipeline does not fetch.
  5. The Xray stage is not yet built or run. Its flow above is a design, not a result.
  6. No negative or risk-focused candidates were requested (the run used 5 core, 0 risk, 0 exploratory). For an API, error and boundary cases are where defects usually hide, so these limits need widening. Interestingly, one core candidate still covered an empty-result case.

Next steps

First, inspect the run manifest to find which of the three explanations holds, and cover the sufficiency gate with a test that fails on a deliberately incomplete request. Second, guard the offline path so it can never reach the real model. Third, finish the Xray steps and complete one real create-and-link run. Fourth, add the scoring step below.

A step that scores the output

The missing piece is a step after "Write": compare the candidates with a set of trusted, hand-written tests for the same endpoints, and count how many candidates are correct, how many are wrong, and what was missed. Run that across ten endpoints and the pipeline has a measured result instead of a demonstration. It is the same principle the pipeline already applies to the model: do not trust the summary, check the evidence.

Rules I would keep

  • The model is one step of eleven. Put the effort into the other ten.
  • Two human gates: approve the scope, then approve the evidence.
  • Missing evidence blocks generation. No fallbacks that guess.
  • Measure the prompt before approval, and store its hash with the result.
  • Read committed content at a named reference, and say plainly what is unverified.
  • Use an obvious placeholder for any unverified key, never a plausible guess.
  • Review-only by default: a person decides what becomes a real test.
  • Treat open questions as a BA agenda, and treat a contract fact in that agenda as a bug.
  • Test the gates themselves. A gate nobody has tried to bypass is an assumption.
  • Draw the graph. Every dashed edge that skips a check needs a test.
  • Every write to a shared system gets its own approval and a read-back.

Summary and conclusion

This article set out to describe a pipeline that drafts API and UI test candidates without trusting the model more than it deserves. The approach is to gather evidence deterministically through local, read-only MCP servers, to place two human gates around that evidence, and to block generation whenever a required item is missing. The main finding so far is that the safety of such a system comes less from the model than from the structure around it: the gates, the sufficiency rule and the recorded evidence. A second finding is that the open questions are as valuable as the candidate tests, because they turn gaps in the requirements into a ready agenda for the business analyst, and, read carefully, they can also point to gaps in the pipeline itself. The structure, however, is only as strong as its weakest gate, so the gates must be tested, and the quality of the output still has to be measured. The next stage, publishing approved candidates to Xray, applies the same principle to writing: every write is approved by a person and confirmed by reading it back. Those are the next steps.

If you build something similar at work, ask your employer first, use only approved tools and model endpoints, and keep real system names, tickets and data out of anything you publish.
