How I built a "second brain" for test automation with Claude Code and Obsidian (and tested it like a QA engineer)

A step-by-step guide to an Andrej Karpathy-style LLM knowledge base: rough notes in, a linked wiki out, answers that cite their sources, and a guard that stops secrets reaching the model.

Matt Karimov · Test automation engineer · October 2026

Every test automation engineer I know carries a private pile of knowledge around in their head. Which environment falls over at 8am. Why the parallel runner is capped at six threads. The one locator that only works if you wait for the dashboard, not the login page. How to reset test data without raising a ticket.

Most of it never gets written down properly. When it does, it lands in a chat thread or a scratch file that nobody, including me, can find three months later. AI coding assistants don't help here on their own: every session starts from zero, and you explain the same context again.

Andrej Karpathy described a simple alternative: let an LLM maintain a personal wiki for you. You drop rough notes into a folder, and the model "compiles" them into linked, well-structured pages with an index. You then ask questions against that wiki rather than against your memory. No vector database, no embeddings, just markdown and a good index.

I built this with Claude Code as the compiler and Obsidian as the viewer, and then did what I do for a living: I tested it. This article gives you every file and command you need to set it up yourself, plus what I learned from testing it.

Before you use this at work: check your employer's policy. Use only an AI tool your organisation has approved for internal material, keep the folder on approved storage, and never put customer data, credentials or production details into it. Everything in this article was built and tested on my own machine with made-up notes.

The idea in QA terms

If you work in test automation, the pattern maps neatly onto things you already know:

Knowledge base Software build Who writes it
raw/: your rough notes source code you only
/compile the build Claude Code
wiki/: linked pages the build artefact Claude Code only
/lint the test suite a script plus Claude
/query running the product Claude Code, citing pages

Two rules come straight from that table:

  1. Raw notes are append-only. The model never edits them. They're your source of truth.
  2. The wiki is disposable. Anything in wiki/ can be regenerated from raw/, so the model can rewrite it freely, and you never edit it by hand.

Two ways to build it, and why I chose the manual one

There is a popular open-source kit, claude-memory-compiler by Cole Medin, that does this automatically. Claude Code hooks capture each session when it ends, a background job extracts the lessons into a daily log, and a nightly step compiles the wiki. I installed it on a personal project and it's clever.

When I tested it, though, every session was being saved as "nothing worth saving". Root cause: the background summariser was itself a Claude session, so the kit's own start-up hook injected old log text into it, including the literal marker FLUSH_OK. The model echoed the marker, and the code checked whether the reply contained FLUSH_OK rather than whether it was FLUSH_OK, so it threw away every real summary. Fixing it took two small changes: skip the start-up hook inside the summariser, and match the marker exactly. That's a classic QA lesson. The code ran without errors and still did nothing useful. Only checking the actual output caught it.

For work, I still chose a manual design, for three reasons:

  • Nothing runs in the background. Auto-capture sends whole session transcripts to the model provider. At work I want to decide exactly what goes in.
  • Every compile is guarded. A plain script scans the notes for secrets before the model reads them.
  • It's easy to audit. Four slash commands, three small Python scripts, one rules file. No packages to install.

The rest of this article builds the manual version, which I call a Work Brain.

What you need

  • Claude Code, signed in with an account you're allowed to use for this material (claude in a terminal, or the IntelliJ or VS Code extension).
  • Python 3.8 or newer. Only the standard library is used. On Windows the command is often py.
  • Obsidian (optional, but it's what makes the wiki pleasant to read).
  • About 30 minutes.

Step 1: Create the folder

mkdir -p work-brain/{.claude/commands,tools,raw,wiki} && cd work-brain
git init

Git is optional but useful: it gives you history for raw/ and lets you see exactly what each compile changed in wiki/, the same way you'd review a diff.

Create the two starting files in wiki/:

printf '# Index\n\n| Page | Type | Summary | Updated |\n|---|---|---|---|\n' > wiki/index.md
printf '# Build log (append only)\n' > wiki/log.md

Step 2: Write the rules file, CLAUDE.md

Claude Code reads CLAUDE.md automatically at the start of every session in that folder. This is where the whole design lives: who owns which folder, what may never be copied, and what a page looks like. Here's the core of mine (the full file is in the repository):

# CLAUDE.md: Work Brain (LLM knowledge base, Karpathy pattern)

You (Claude Code) are the compiler and librarian of this knowledge base.
The human writes rough notes; you turn them into a linked, queryable wiki.

## Ownership rule (non-negotiable)
| Path | Only writer | Rule |
|---|---|---|
| raw/ | human | Never edit, rename or delete. Read only. |
| wiki/ | Claude | Rewrite freely. Everything can be regenerated from raw/. |
| wiki/index.md | Claude | Updated on every compile. The retrieval entry point. |
| wiki/log.md | Claude | Append only. |
| CLAUDE.md, tools/, .claude/ | human | Do not modify. |

## Data rules (these override everything)
1. No client or customer data (names, account numbers, sort codes, IBANs,
   card numbers, addresses, dates of birth).
2. No credentials (passwords, tokens, keys, connection strings, cookies).
3. No production data or production hostnames. Test environments by role only.
4. Colleagues are referred to by role, not name.
5. If a raw note contains any of the above, do not copy it into the wiki.
   Write the knowledge without the value (e.g. "the SIT DB user is in the
   team vault") and report the file and line to the human.
6. Never use web tools in this repo. Knowledge comes from raw/ only.

## Page types (folders under wiki/)
| Folder | One page per |
|---|---|
| systems/ | service, component or environment |
| howto/ | repeatable procedure |
| decisions/ | decision with its reason (ADR-style) |
| defects/ | recurring failure pattern and its fix |
| concepts/ | idea, pattern or domain term |
| qa/ | answered question filed back by /query |

## Page format
Every page has YAML front matter (title, type, tags, sources, created,
updated, status: current | needs-check | superseded), then:
a 2-4 sentence summary, Key points, Details, Related ([[links]]), Sources.

Rules:
- Links are Obsidian [[folder/slug]]. Every page links to at least one other page.
- Prefer updating an existing page over creating a near-duplicate.
- If two sources disagree, keep both claims and mark status: needs-check.
  Never resolve a contradiction by guessing.
- Write only what the sources say. Label your own inferences "(inferred)".

The page types are the QA-specific part. A general-purpose second brain has "concepts" and "people". A testing one needs defects (recurring failure patterns and their fixes), how-tos (repeatable procedures like resetting test data) and decisions (why the suite is configured the way it is). Those three are where most lost knowledge comes from.

Step 3: Lock down permissions, .claude/settings.json

This is the part most guides skip. Instructions in CLAUDE.md are requests. Permissions in settings.json are enforced by Claude Code itself. I let Claude write only to wiki/, run only the three helper scripts, and I deny web access and any edits to my notes, the rules or the tools:

{
  "permissions": {
    "allow": [
      "Read(./**)",
      "Edit(./wiki/**)",
      "Bash(python3 tools/guard.py:*)",
      "Bash(python3 tools/lint.py:*)",
      "Bash(python3 tools/new_note.py:*)",
      "Bash(python tools/guard.py:*)",
      "Bash(python tools/lint.py:*)",
      "Bash(python tools/new_note.py:*)",
      "Bash(py tools/guard.py:*)",
      "Bash(py tools/lint.py:*)",
      "Bash(py tools/new_note.py:*)"
    ],
    "deny": [
      "WebFetch",
      "WebSearch",
      "Edit(./raw/**)",
      "Edit(./CLAUDE.md)",
      "Edit(./tools/**)",
      "Edit(./.claude/**)"
    ]
  }
}

The three spellings of Python (python3, python, py) cover Linux, macOS and Windows. One detail I learned the hard way: in Claude Code, Edit(path) rules cover every file-writing tool, so don't add a separate Write(path) rule. Claude Code warns that it isn't matched.

Step 4: The guard, tools/guard.py

Before the model reads a single note, a plain script scans raw/ for things that must never leave your machine. A regex gives the same answer every time; a model "being careful" might not. It exits with code 1 if it finds anything, and /compile refuses to continue. It never prints the full value, only the first three characters.

#!/usr/bin/env python3
"""Sensitive-data guard. Stdlib only, Python 3.8+.
Exit 0 = clean, 1 = findings (compile must stop)."""
import re
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent

PATTERNS = [
    ("private key", re.compile(r"-----BEGIN [A-Z ]*PRIVATE KEY-----")),
    ("AWS access key", re.compile(r"\b(AKIA|ASIA)[0-9A-Z]{16}\b")),
    ("JWT / bearer token", re.compile(r"\beyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{5,}")),
    ("GitLab/GitHub token", re.compile(r"\b(glpat-[A-Za-z0-9_-]{20,}|gh[pousr]_[A-Za-z0-9]{30,})\b")),
    ("password/secret assignment",
     re.compile(r"(?i)\b(password|passwd|pwd|secret|api[_-]?key|token|client[_-]?secret)\b\s*[:=]\s*\S{4,}")),
    ("connection string with credentials", re.compile(r"(?i)\b[a-z][a-z0-9+.-]*://[^\s:/@]+:[^\s@]+@")),
    ("IBAN", re.compile(r"\b[A-Z]{2}\d{2}(?: ?[A-Z0-9]{4}){3,7}(?: ?[A-Z0-9]{1,4})?\b")),
    ("sort code", re.compile(r"\b\d{2}-\d{2}-\d{2}\b")),
    ("email address", re.compile(r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b")),
    ("UK National Insurance number", re.compile(r"\b[A-CEGHJ-PR-TW-Z]{2}\s?\d{2}\s?\d{2}\s?\d{2}\s?[A-D]\b")),
]
CARD = re.compile(r"\b(?:\d[ -]?){13,19}\b")


def luhn_ok(digits: str) -> bool:
    """Only flag card-like numbers that pass the Luhn check (fewer false positives)."""
    total, alt = 0, False
    for ch in reversed(digits):
        d = int(ch)
        if alt:
            d *= 2
            if d > 9:
                d -= 9
        total += d
        alt = not alt
    return total % 10 == 0


def load_allow():
    """Known false positives: one regex per line in tools/guard-allow.txt."""
    f = ROOT / "tools" / "guard-allow.txt"
    if not f.exists():
        return []
    return [re.compile(x.strip()) for x in f.read_text(encoding="utf-8").splitlines()
            if x.strip() and not x.startswith("#")]


def mask(s: str) -> str:
    s = s.strip()
    return s[:3] + "…" if len(s) > 3 else "…"


def scan(folder: Path):
    allow = load_allow()
    findings = []
    for path in sorted(folder.rglob("*.md")):
        for n, line in enumerate(path.read_text(encoding="utf-8", errors="replace").splitlines(), 1):
            if any(a.search(line) for a in allow):
                continue
            for label, rx in PATTERNS:
                for m in rx.finditer(line):
                    findings.append((path, n, label, mask(m.group(0))))
            for m in CARD.finditer(line):
                digits = re.sub(r"\D", "", m.group(0))
                if 13 <= len(digits) <= 19 and luhn_ok(digits):
                    findings.append((path, n, "card number (Luhn valid)", mask(digits)))
    return findings


def main():
    target = "wiki" if "--wiki" in sys.argv else "raw"
    folder = ROOT / target
    if not folder.exists():
        print(f"guard: {target}/ not found")
        return 0
    findings = scan(folder)
    if not findings:
        print(f"guard: {target}/ clean")
        return 0
    print(f"guard: {len(findings)} finding(s) in {target}/. Remove these before compiling:")
    for path, n, label, shown in findings:
        print(f"  {path.relative_to(ROOT)}:{n}  {label}  ({shown})")
    return 1


if __name__ == "__main__":
    sys.exit(main())

Add patterns for your own organisation's identifiers, such as internal ticket formats or hostname conventions you don't want in prompts. Be honest about its limits, though: a regex can't recognise a client's name or a production hostname that looks like any other word. The guard is a safety net, not permission to be careless.

Step 5: Change detection, tools/lint.py

This script does two jobs where you want exact bookkeeping rather than the model's judgement.

Job 1: which notes need compiling? Each time Claude compiles a note, it writes the note's fingerprint (a short SHA-256 hash) into wiki/log.md. Next time, the script compares fingerprints. A note it has never seen is new. A note whose content has changed, such as an Obsidian daily note you added to in the afternoon, is changed. Anything else is skipped. This is what makes /compile safe to run as often as you like.

SOURCE = re.compile(r"^- Source:\s*(raw/\S+?)(?:\s*\(sha ([0-9a-f]{6,})\))?\s*$", re.M)


def sha(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()[:12]


def compiled_sources() -> dict:
    """raw path -> set of hashes already compiled, read from wiki/log.md."""
    log = WIKI / "log.md"
    out = {}
    if log.exists():
        for path, h in SOURCE.findall(log.read_text(encoding="utf-8")):
            out.setdefault(path, set()).add(h or "")
    return out


def uncompiled():
    """List of (raw path, current sha, 'new' | 'changed'). Empty notes are skipped."""
    done = compiled_sources()
    raws = sorted(p for p in RAW.rglob("*.md") if p.name.lower() != "readme.md") if RAW.exists() else []
    todo = []
    for p in raws:
        if not p.read_text(encoding="utf-8", errors="replace").strip():
            continue
        rel, h = p.relative_to(ROOT).as_posix(), sha(p)
        seen = done.get(rel)
        if seen is None:
            todo.append((rel, h, "new"))
        elif h not in seen and "" not in seen:
            todo.append((rel, h, "changed"))
    return todo

Job 2: is the wiki healthy? Running it with no arguments checks for broken [[links]], orphan pages (nothing links to them), pages missing from the index, missing front matter, and very thin pages. It exits with code 1 on errors, so you could run it in CI if the wiki lives in a shared repository. The full script (about 140 lines) is in the repository.

python3 tools/lint.py --uncompiled   # what needs compiling
python3 tools/lint.py                # full health report

Step 6: The safe note writer, tools/new_note.py

When you'd rather paste a note into Claude Code than open Obsidian, /ingest uses this script. It opens the file in exclusive-create mode ("x"), so it physically cannot overwrite an existing note:

#!/usr/bin/env python3
"""Create a NEW raw note from stdin. Refuses to overwrite: raw/ is append-only."""
import re
import sys
from datetime import date
from pathlib import Path

RAW = Path(__file__).resolve().parent.parent / "raw"


def main():
    if len(sys.argv) < 2:
        print("usage: new_note.py <topic>  (text on stdin)")
        return 2
    topic = " ".join(sys.argv[1:]).strip()
    body = sys.stdin.read().strip()
    if not body:
        print("new_note: empty text, nothing saved")
        return 2
    slug = re.sub(r"[^a-z0-9]+", "-", topic.lower()).strip("-")[:50] or "note"
    RAW.mkdir(exist_ok=True)
    base = f"{date.today().isoformat()}-{slug}"
    path, n = RAW / f"{base}.md", 2
    while path.exists():
        path, n = RAW / f"{base}-{n}.md", n + 1
    with open(path, "x", encoding="utf-8") as f:  # "x" = fail if it exists
        f.write(f"# {topic}\n\n{body}\n")
    print(f"saved {path.relative_to(RAW.parent).as_posix()}")
    return 0


if __name__ == "__main__":
    sys.exit(main())

Step 7: The four slash commands

Any markdown file in .claude/commands/ becomes a slash command in Claude Code. The front matter limits which tools that command may use, and $ARGUMENTS is whatever you type after the command.

.claude/commands/compile.md, the build:

---
description: Compile uncompiled raw notes into wiki pages (guard runs first)
allowed-tools: Read, Write, Edit, Glob, Grep, Bash(python tools/guard.py:*), Bash(python3 tools/guard.py:*), Bash(python tools/lint.py:*), Bash(python3 tools/lint.py:*)
---

Follow CLAUDE.md exactly.

1. Run `python3 tools/guard.py` (use `python` if `python3` is not found).
   - If it exits non-zero, **stop**. Show the findings and tell the human to remove those
     values from the raw notes. Do not compile anything.
2. Run `python3 tools/lint.py --uncompiled`. Each line is `raw/<file> (sha <hash>) new|changed`.
   If it prints "Nothing to compile", say so and stop.
   - `new`: compile the whole note.
   - `changed`: the note was compiled before and has had text added (e.g. an Obsidian daily
     note). Read it in full, then fold only the new material into the pages.
3. Read `wiki/index.md`, then the existing pages it points to that look relevant.
4. For each uncompiled raw file, oldest first:
   - Extract systems, how-tos, decisions, defects and concepts.
   - Update existing pages where they cover the topic; create new pages only for new topics.
   - Apply the data rules: never carry a sensitive value into the wiki.
   - Mark disagreements between sources `status: needs-check`.
5. Update `wiki/index.md` (one row per page, sorted by type then page).
6. Append one entry per raw file to `wiki/log.md` with `- Source:`, `- Created:`, `- Updated:`
   and `- Withheld:` lines. The Source line must copy the hash exactly as listed in step 2:
   `- Source: raw/<file> (sha <hash>)`. Without it the note is offered for compile again.
7. Run `python3 tools/lint.py` and fix any broken links you introduced.
8. Report: files compiled, pages created, pages updated, anything withheld, anything marked
   needs-check. Keep it short.

$ARGUMENTS

.claude/commands/query.md, grounded answers:

---
description: Answer a question from the wiki, cited to pages
allowed-tools: Read, Glob, Grep, Write, Edit
---

Question: $ARGUMENTS

Follow CLAUDE.md.

1. Read `wiki/index.md` first. Pick the 3–10 pages most likely to answer the question.
2. Read those pages in full. Use `raw/` only if the wiki is silent, and say so.
3. Answer in plain language. After each claim, cite the page as `[[folder/slug]]`.
4. If the wiki does not contain the answer, say **"The wiki does not cover this"** and name the
   closest pages. Do not answer from general knowledge without labelling it `(not from wiki)`.
5. If any cited page has `status: needs-check`, say so.
6. End by asking: "File this answer to wiki/qa/? (yes/no)". If the human says yes, write the
   `qa/` page, add it to `wiki/index.md`, and append a `query` entry to `wiki/log.md`.

Step 4 is the line I care about most as a tester. An assistant that says "I don't know" when it doesn't know is worth far more than one that answers everything confidently.

.claude/commands/lint.md, the test suite:

---
description: Health-check the wiki (structure + contradictions)
allowed-tools: Read, Glob, Grep, Edit, Bash(python tools/lint.py:*), Bash(python3 tools/lint.py:*), Bash(python tools/guard.py:*), Bash(python3 tools/guard.py:*)
---

1. Run `python3 tools/guard.py --wiki` (or `python`) and report any sensitive values found in `wiki/`.
2. Run `python3 tools/lint.py` and show its report.
3. Read the pages and look for **contradictions** between them (different values, steps or
   decisions for the same thing). For each one, list both pages and the conflicting claims.
   Do not fix contradictions; mark both pages `status: needs-check`.
4. List pages whose `updated` date is more than 90 days old as "possibly stale".
5. Offer fixes for broken links and orphan pages. Apply them only if the human says yes.

$ARGUMENTS

The script handles what can be checked mechanically. The model handles what needs reading comprehension, such as two pages giving different thread limits for the same suite.

.claude/commands/ingest.md, quick capture:

---
description: Save a new raw note (new file only, never edits)
allowed-tools: Bash(python tools/new_note.py:*), Bash(python3 tools/new_note.py:*), Bash(python tools/guard.py:*), Bash(python3 tools/guard.py:*)
---

Save the text below as a new raw note. Do not use Write or Edit on `raw/`; use the script, which
refuses to overwrite:

    python3 tools/new_note.py "<short topic>" <<'EOF'
    <the text, verbatim>
    EOF

(Use `python` if `python3` is not found.) Then run `python3 tools/guard.py` and report any
findings. Do not compile. Reply with the saved file name in one line.

Text:
$ARGUMENTS

Step 8: Connect Obsidian

  1. In Obsidian, use Open folder as vault and choose work-brain, or put work-brain inside your existing vault as one folder.
  2. Go to Settings → Core plugins → Daily notes and set New file location to work-brain/raw and Date format to YYYY-MM-DD.
  3. In Settings → Files and links, turn on Use [[Wikilinks]].

Now your daily note is a raw note. Write rough bullets during the day and they're picked up at the next compile, including anything you add after the last one, thanks to the fingerprints from step 5.

If your vault syncs through OneDrive or a similar service, mark the folder Always keep on this device so the scripts read real files rather than cloud placeholders. Remember that synced storage keeps old versions, so a secret you delete later still exists in the file history. That's another reason the guard runs before anything is written.

Step 9: First run

Start Claude Code in the folder:

cd work-brain
python3 tools/lint.py     # expect: Pages: 0  Errors: 0
python3 tools/guard.py    # expect: guard: raw/ clean
claude

Inside Claude Code, type / and check that compile, query, lint and ingest appear. Then add a note. Here's one of the made-up notes I tested with:

# karate parallel runs

Karate suite was slow (40 min). Switched runner to Runner.path("classpath:features").parallel(6).
Now 9 min on GitLab runner.
Gotcha: features that share the same test customer collide in parallel. Tag them @serial and run
them in a separate job.
Decision: max 6 threads, because the SIT payments stub rate-limits above ~8 concurrent calls.

Then run:

/compile

From three short notes like this one, Claude produced five linked pages: a how-to (Run Karate in parallel), a decision (Karate max six threads), a defect (Flaky Playwright login), another how-to (Reset SIT test data) and a system page (SIT environment) that combined facts from all three notes. It also filled in wiki/index.md:

| Page | Type | Summary | Updated |
|---|---|---|---|
| [[decisions/karate-max-six-threads]] | decision | Karate runs capped at 6 threads because the SIT payments stub rate-limits above ~8 concurrent calls | 2026-10-21 |
| [[defects/flaky-playwright-login]] | defect | Login test flaked 1 in 10 on CI because of a late SSO redirect; fixed by waiting for the dashboard locator | 2026-10-21 |
| [[howto/run-karate-in-parallel]] | howto | Parallel Karate runner (6 threads, 40 to 9 min); tag shared-customer features @serial in a separate job | 2026-10-21 |
| [[systems/sit-environment]] | system | Shared SIT test environment: 08:00 batch job, payments stub limit, DB access via the team vault | 2026-10-21 |

That index is the whole retrieval system. When you run /query, Claude reads these one-line summaries first, opens only the relevant pages, and answers from those. Karpathy's point is that at personal scale, a few hundred pages, an LLM reading a well-kept index works better than a vector database, and there's nothing to keep in sync. Beyond that size you'd add search.

Testing it like a QA engineer

I don't trust a tool because its output looks plausible. Before using this for anything real, I wrote down what should happen and checked each case. These are the tests I ran, all with made-up notes.

1. Negative test: does the guard block a secret? I put a fake password line in one note and ran /compile. The guard reported the file, line number and the type of finding (password/secret assignment), showing only the first three characters. Claude stopped, told me what to fix, and wrote nothing to wiki/. Pass.

2. Does the knowledge survive without the secret? I replaced the line with "credentials are in the team vault (SIT entry)" and compiled again. The SIT environment page kept the useful fact ("SIT DB credentials are in the team vault, under the SIT entry. Ask the env team for a read-only DB role.") without any value. Afterwards I searched the whole folder for the fake password: zero hits. Pass.

3. Idempotence: does a second compile duplicate anything? Running /compile again with no new notes returned "Nothing to compile". Pass.

4. Change detection: is a growing daily note picked up? I added a line to a note that had already been compiled. lint.py --uncompiled listed it once as changed, Claude folded in only the new material, and the next check listed nothing. Pass.

5. Contradictions: does it guess? The added line said a flaky test had come back, contradicting an earlier "no more flakes in 50 runs". Claude kept both statements, explained the conflict, and marked the page status: needs-check instead of picking a winner. Pass.

6. Grounding: does it refuse when the wiki is silent? I asked how to reset Kafka consumer group offsets in UAT, which none of my notes mention. The answer began "The wiki does not cover this" and named the closest pages. Pass.

7. Structure: is the build clean? lint.py reported 0 errors after the compile, and guard.py --wiki reported the wiki clean.

These are manual checks on a tiny sample, not a benchmark. They tell me the controls work as designed, not that the model will summarise every note perfectly. That's why the wiki cites its sources, so you can always check a page against the note it came from.

Rules I'd keep

  • Ask first. Check your organisation's AI and data policy before you put any work notes into an AI tool, and use only the tools and accounts it approves.
  • Never write a secret in a note in the first place. The guard is a net, not a licence.
  • Enforce, don't just ask. Put the important rules in settings.json permissions, not only in CLAUDE.md.
  • Keep raw notes append-only. They're your source of truth; the wiki is a build artefact.
  • Never let the model settle a contradiction. Mark it and let a human decide.
  • Prefer "I don't know" to a confident guess. Make refusal an explicit step in /query.
  • Test the controls yourself. Plant a fake secret and confirm the compile stops before you trust it with real notes.

Limits

  • The guard catches patterns (keys, tokens, card numbers, IBANs, sort codes, emails, NI numbers). It can't recognise client names, internal project names or production hostnames.
  • Compile quality depends on the notes. Vague notes produce vague pages, and the model can still misread one, so check pages against their sources.
  • Index-based retrieval suits hundreds of pages, not tens of thousands.
  • Every compile and query uses your Claude Code plan or API budget.

Why this matters for QA

Most of what makes a test automation engineer effective in a team is context, not code: why things are configured the way they are, which failures are known, and how to get unstuck. A second brain doesn't replace a team wiki, but it gives you a private place where that context accumulates instead of evaporating.

Building it was also good practice for the job I want next, testing AI systems. The same questions apply to any LLM feature: does it refuse when it should, does it stay grounded in its sources, does it leak what it shouldn't, and do its controls hold when you deliberately try to break them?
