Hosting a Next.js Shop on a Raspberry Pi 5: Docker, Cloudflare Tunnel and WireGuard, Step by Step

Dusmamat (Matt) Karimov · 8 November 2026 · 20 min read

This guide records how a demonstration shop runs on a Raspberry Pi 5 in a private home: how the application was packaged with Docker, how Cloudflare publishes it without opening any port for the website, and how the Pi is administered from a phone over WireGuard and SSH in Termux. Every file reproduced below is the one running on the Pi on 8 November 2026, whereas secrets, keys, the tunnel identifier, the domain and the project name have been replaced by placeholders.

It should be noted at the outset that the shop is a learning project rather than a business, since it runs on Stripe test keys and has never taken an order. This guide therefore does not describe how to operate a trading shop. Rather, it records a working, production-shaped setup that suits a demonstration, a portfolio piece or a low-stakes service, and its final section explains why the same setup falls short of what a real business requires. The costs, risks and lessons of the same setup are argued separately in a companion article, The Four-Pound Storefront, which this guide therefore does not repeat at length.

The overall structure of this guide is organised as follows: the first part lists what is needed and shows how the pieces fit together; Steps 1 to 4 package the application and run it with Docker Compose; Steps 5 and 6 register the domain and publish the site through a Cloudflare Tunnel; Step 7 sets up remote administration with WireGuard and Termux; Step 8 covers backups and updates; Step 9 records the checks used to test the result; and the guide closes with the rules worth keeping and a summary and conclusion.

What you need

Item Measured on the Pi
Computer Raspberry Pi 5, 8 GB RAM
Storage 1 TB NVMe SSD, used for the OS and the data
OS Raspberry Pi OS on Debian 13 (trixie), 64-bit
Containers Docker Engine 29.9.2, Docker Compose v5.6.1
Application Next.js 14.1, Prisma 5, SQLite
Edge Cloudflare account, a Cloudflare Registrar domain, cloudflared 2026.2.0
Remote access WireGuard (wg-quick) on the Pi; WireGuard and Termux on an Android phone

According to the registrar's dashboard, the .co.uk domain renews at $5.30 a year, which was £3.97 on 8 November 2026. The Pi draws about 3 W, which amounts to roughly £6.82 a year of electricity at the October to December 2026 price cap; however, the same Pi also runs 14 other containers, so the shop's own share of that electricity is a matter of pennies.

How the pieces fit

Visitor  --HTTPS-->  Cloudflare edge (DNS + TLS)
                          |
                  Cloudflare Tunnel  (an OUTBOUND connection the Pi opens)
                          |
        cloudflared on the Pi  -->  http://localhost:3000  -->  app container  -->  SQLite volume

Phone (Termux)  --WireGuard, UDP 51820-->  Pi at 10.8.0.1  --SSH-->  shell

In other words, visitors never connect to the house: the Pi opens an outbound connection to Cloudflare, and Cloudflare then answers the visitors on its behalf. The router forwards exactly one port, UDP 51820 for WireGuard, and that port serves remote administration rather than visitors.

Step 1: Prepare the Pi

  1. Install Raspberry Pi OS (64-bit) on the NVMe drive and boot from it, since a solid-state drive is generally faster and more durable than a memory card for a server that writes logs and a database every day.
  2. Install Docker Engine and the Compose plugin from Docker's own apt repository, following docs.docker.com/engine/install/debian, and then add the user to the docker group and log in again.
  3. Confirm that both work before going any further:
docker run --rm hello-world
docker compose version

The exact install commands were not recorded at the time; the result on this Pi is Docker 29.9.2 with Compose v5.6.1.

Pitfall: docker stats reports 0 B of memory on this Pi. Memory accounting (cgroup_enable=memory) is not switched on in /boot/firmware/cmdline.txt, and therefore Docker cannot see the figure at all; the host's own process table, however, can:

docker top <container> -eo pid,rss,comm      # RSS in KB per process

Measured in this way, the shop's application uses 213 MB rather than the zero that Docker reports, which is a reminder that a tool's silence is not the same thing as a measurement.

Step 2: Make the application container-ready

Two files decide what enters the image. First, next.config.js turns on Next.js standalone output, which produces a small server.js bundle containing only the dependencies that the server actually needs:

/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone',
  // images.remotePatterns: unchanged, omitted here
}

Second, .dockerignore keeps secrets, local databases, uploads and build leftovers out of the build context, so that none of them can ever end up inside an image layer:

Step 3: The Dockerfile

The full file follows, and its comments record the real history of what went wrong while it was being written.

FROM node:20 AS base

FROM base AS deps
WORKDIR /app

COPY package.json package-lock.json* ./
RUN npm ci

FROM base AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .

ENV NEXT_TELEMETRY_DISABLED 1

# Build-time placeholders only. Real secrets are supplied at runtime — passing
# them as build ARGs bakes them into image layers, readable via `docker history`.
# The build needs these variables to exist, not to be valid.
#
# `/` is statically prerendered and queries Prisma, so the build needs a
# database that has the tables. This throwaway one is never shipped: the
# runtime stage copies only .next/standalone, .next/static and public.
ENV DATABASE_URL="file:/tmp/build-placeholder.db"
ENV STRIPE_SECRET_KEY="sk_test_build_placeholder"
ENV SESSION_SECRET="build-time-placeholder-secret-32-chars-min"

RUN npx prisma db push --skip-generate && npm run build

FROM base AS runner
WORKDIR /app

ENV NODE_ENV production
ENV NEXT_TELEMETRY_DISABLED 1

RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 nextjs

COPY --from=builder /app/prisma ./prisma
COPY --from=builder /app/package.json ./package.json
COPY --from=deps /app/node_modules ./node_modules

RUN npm install sharp

RUN mkdir -p /app/data
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public

RUN chown -R nextjs:nodejs /app

USER nextjs

EXPOSE 3000

ENV PORT 3000
ENV HOSTNAME "0.0.0.0"

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/api/health', (r) => {process.exit(r.statusCode === 200 ? 0 : 1)})"

# Apply versioned migrations only. The previous `db push --accept-data-loss`
# plus an unconditional re-seed ran on every restart, which reset the admin
# password and overwrote product rows edited through the admin UI.
# Seeding is a one-time provisioning step: `npm run prisma:seed`.
CMD npx prisma migrate deploy && node server.js

Each stage has a single purpose. The deps stage installs exactly what package-lock.json specifies through npm ci. The builder stage creates a throwaway SQLite database before it builds, because the home page is prerendered at build time and reads products from the database; without a database that already has the tables, next build therefore fails at "Generating static pages". The runner stage is the image that actually runs: it uses a non-root user (nextjs, uid 1001), checks its own health every 30 seconds, applies database migrations, and only then starts the server.

The comments record two lessons. First, secrets passed as build arguments are readable by anyone who holds the image through docker history, and for this reason the build receives harmless placeholders while the real values arrive only at runtime. Second, prisma db push --accept-data-loss, combined with a seed on every start, once reset the admin password and overwrote product edits at each restart; the start command therefore runs prisma migrate deploy, and seeding happens exactly once.

One weakness remains unfixed, namely that the image occupies 3.17 GB. According to docker history, three layers account for most of that size:

Layer Size Why
COPY --from=deps /app/node_modules 618 MB full dependency tree, kept because the start command runs npx prisma migrate deploy, which needs the Prisma CLI
Debian packages in node:20 591 MB the full base image
RUN chown -R nextjs:nodejs /app 508 MB rewrites files that are already there, so Docker stores them twice

It seems that each of these can be reduced, although none of the following ideas has yet been tested on this Pi: using COPY --chown for every copy and changing the ownership of /app/data alone; installing only the Prisma CLI in the runner; and trying the node:20-slim base. Each change should therefore be proved on a spare container before it replaces the live one.

The .env file sits beside it with permissions 600. The variable names below are those of .env.example, whereas every value shown is a placeholder:

chmod 600 .env

The application is then built and started:

docker compose build app
docker compose up -d
docker compose logs -f app

The first start depends on the state of the database. A fresh volume needs nothing further, because prisma migrate deploy creates the tables on first start; the admin user and the products are then provisioned once with npm run prisma:seed, which refuses a default admin password and, if run again, never overwrites an existing password or edited products. A database that existed before migrations were introduced, on the other hand, has to be baselined once, or else the container restart-loops with Prisma error P3005. The following command is the one that worked on this Pi:

docker compose run --rm --no-deps app sh -c \
  "npx prisma migrate resolve --applied 20260812213417_init && npx prisma migrate deploy"

A short check then confirms that the container is healthy and that real data, not merely a health signal, is being served:

docker ps --format '{{.Names}}\t{{.Status}}'        # app shows (healthy)
curl -s http://localhost:3000/api/products | head -c 200

Four pitfalls apply at this step.

  1. A healthy /api/health does not prove a working shop. On one occasion the live .env carried the example SESSION_SECRET, which the application rejects; as a result /api/products returned 500 and the site displayed "No products found", while the health check remained green throughout. A data endpoint should therefore be checked after every deploy.
  2. The mapping "3000:3000" publishes the application on every network interface, so that any device on the home Wi-Fi can reach it directly and bypass Cloudflare altogether. Because the tunnel needs only the Pi itself, the correct mapping is "127.0.0.1:3000:3000", although this fix has not yet been applied on this Pi.
  3. The nginx service is not in the request path at all. The tunnel sends traffic straight to the application on port 3000, and nginx consequently served no requests in the last seven days; it should therefore either receive the tunnel's traffic or be removed from the file.
  4. The database belongs in a named volume such as db-data. On Docker 23 and later, docker volume prune -f removes only anonymous volumes, whereas adding -a would also delete named volumes whose containers happen to be stopped, the shop's database among them.

Step 5: The domain on Cloudflare Registrar

  1. In the Cloudflare dashboard, open Domains and then Registrations to register the name; Cloudflare sells at the registry's own price, and a .co.uk therefore renews at $5.30 a year on this account.
  2. The domain's DNS is then managed within the same Cloudflare account, which is precisely what the tunnel requires in Step 6.
  3. Switch on Auto renew on the domain's Overview page, because on this account the registration runs only to 9 October 2027 and automatic renewal had been left switched off.

Step 6: Publish the application with a Cloudflare Tunnel

The cloudflared package can be installed either from Cloudflare's apt repository or from the arm64 package on Cloudflare's GitHub releases page; this Pi runs version 2026.2.0, although the install route that was used was not recorded.

The tunnel on this Pi is locally managed, that is to say it was created on the command line rather than in the dashboard. The files present on the Pi match that route exactly: a login certificate, a credentials file named after the tunnel's identifier, and a configuration file.

cloudflared tunnel login                  # opens a browser; choose the domain; writes ~/.cloudflared/cert.pem
cloudflared tunnel create shop            # writes ~/.cloudflared/<TUNNEL-UUID>.json
cloudflared tunnel route dns shop example.co.uk
cloudflared tunnel route dns shop www.example.co.uk

The configuration that the service actually reads is /etc/cloudflared/config.yml:

tunnel: <TUNNEL-UUID>
credentials-file: /etc/cloudflared/<TUNNEL-UUID>.json

# Shop ONLY.
# Do not add unrelated projects here: a malformed rule stops the whole
# tunnel and takes the shop offline with it. Other projects get their
# own tunnel + their own systemd unit.
ingress:
  - hostname: example.co.uk
    service: http://localhost:3000
  - hostname: www.example.co.uk
    service: http://localhost:3000
  - service: http_status:404

The credentials are then placed where the service can read them, the configuration is validated, and the service is installed:

sudo mkdir -p /etc/cloudflared
sudo cp ~/.cloudflared/<TUNNEL-UUID>.json /etc/cloudflared/
sudo cp ~/.cloudflared/config.yml /etc/cloudflared/config.yml   # credentials-file must point to /etc/cloudflared/
cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate
cloudflared tunnel --config /etc/cloudflared/config.yml ingress rule https://example.co.uk   # prints the matched service
sudo cloudflared service install
systemctl status cloudflared

The resulting service definition on this Pi reads as follows:

ExecStart=/usr/bin/cloudflared --no-autoupdate --config /etc/cloudflared/config.yml tunnel run

The final check is made from outside the Pi's own view of itself:

curl -sI https://example.co.uk | grep -i '^server'    # server: cloudflare
dig +short @1.1.1.1 example.co.uk                      # Cloudflare addresses, never your home IP

Four pitfalls apply at this step.

  1. The service reads /etc/cloudflared/config.yml, not ~/.cloudflared/config.yml. Editing the copy in the home folder validates cleanly and restarts cleanly, yet it changes nothing; for this reason systemctl cat cloudflared | grep ExecStart should be checked before any edit is made.
  2. Each project should have a tunnel of its own, so that a typing error in a hobby project's rule cannot take down a site that matters, and the catch-all http_status:404 rule must always come last in the list.
  3. The flag --no-autoupdate means that cloudflared never updates itself, and on this Pi it does not update through apt either, because it was installed from a downloaded package with no repository behind it. In other words, the program that faces the internet on the shop's behalf is frozen at version 2026.2.0, from February 2026, until Cloudflare's own apt repository is added.
  4. The tunnel drops and recovers by itself. According to its logs, it recorded 131 connection errors in 15 days, mostly QUIC timeouts concentrated on four poor days, and it reconnected every time; nothing outside the house, however, measures whether visitors noticed, and an external uptime check is therefore the missing piece.

Step 7: Reach the Pi from the phone with WireGuard and Termux

7.1 WireGuard on the Pi

sudo apt install wireguard
wg genkey | sudo tee /etc/wireguard/pi.key | wg pubkey | sudo tee /etc/wireguard/pi.pub

The commands above are the standard key-generation route; how the keys on this Pi were generated was not recorded.

The configuration /etc/wireguard/wg0.conf follows with its keys removed, and the addresses shown are examples inside the Pi's 10.8.0.0/24 range.

[Interface]
Address = 10.8.0.1/24
ListenPort = 51820
PrivateKey = <PI-PRIVATE-KEY>
MTU = 1420
PostUp = iptables -A FORWARD -i %i -j ACCEPT; iptables -A FORWARD -o %i -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE; sysctl -w net.core.rmem_max=26214400; sysctl -w net.core.wmem_max=26214400
PostDown = iptables -D FORWARD -i %i -j ACCEPT; iptables -D FORWARD -o %i -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
PublicKey = <PHONE-PUBLIC-KEY>
AllowedIPs = 10.8.0.2/32

[Peer]
PublicKey = <SECOND-DEVICE-PUBLIC-KEY>
AllowedIPs = 10.8.0.3/32

The PostUp line performs two tasks. To be more precise, it lets traffic pass in and out of the tunnel and translates it through eth0, so that the phone can reach the rest of the home network through the Pi, while its two sysctl values raise the UDP buffer sizes. Forwarding must also be switched on (net.ipv4.ip_forward = 1), as it already is on this Pi, after which the interface is enabled:

sudo systemctl enable --now wg-quick@wg0
sudo wg show          # peers and their latest handshake

7.2 The router and the home address

WireGuard needs exactly one forwarded port, and on this setup the router forwards UDP 51820 to the Pi. Because WireGuard answers only those packets that are signed by a known key, the port appears closed to everyone else on the internet.

The home connection, however, has no fixed public IP address: the provider assigns one dynamically from its own range, and no dynamic DNS updater runs on the Pi. The phone's profile does in fact hold the current address itself, as its endpoint field shows, and it therefore stops working whenever the provider changes that address, until it is edited by hand. A dynamic DNS name would remove this weakness, for example a DNS-only record kept up to date through Cloudflare's API. It should be noted, though, that such a record publishes the home address in public DNS, which is exactly what the tunnel otherwise keeps hidden, and a hostname on a separate domain, unrelated to the shop, therefore limits what the record reveals.

7.3 The phone's WireGuard profile

The profile below reproduces the phone's settings as its WireGuard app displays them, with the keys and the home address replaced by placeholders, since the phone's own file is not stored on the Pi.

[Interface]
PrivateKey = <PHONE-PRIVATE-KEY>
Address = 10.8.0.2/32

[Peer]
PublicKey = <PI-PUBLIC-KEY>
Endpoint = <HOME-PUBLIC-IP>:51820
AllowedIPs = 0.0.0.0/0, ::/0
PersistentKeepalive = 25

The phone's profile sends everything through the house. Its AllowedIPs line reads 0.0.0.0/0, ::/0, so that whenever the tunnel is switched on, all of the phone's traffic, and not merely its traffic to the Pi, leaves through WireGuard and reaches the internet over the home broadband line. The counters on the Pi confirm that this route is used in practice, since the Pi has sent the phone almost 1 GB and received about 47 MB since it last started on 24 October. Interestingly, the ::/0 half routes IPv6 into a tunnel that carries IPv4 only, because neither the Pi's interface nor its PostUp rules handle IPv6; in other words, IPv6 traffic is dropped rather than leaked, and applications fall back to IPv4.

This full-tunnel choice has a clear advantage on public Wi-Fi, where it protects all of the phone's traffic. On the other hand, it carries everyday browsing over the home upload line and through the Pi itself. For administration alone, AllowedIPs = 10.8.0.0/24 would carry only the traffic meant for the Pi, whereas adding the home network's range would also reach the other devices at home.

It should also be noted that the second peer in wg0.conf has not connected once since the Pi last started. An unused key remains a standing credential, and it should therefore be removed unless a device still needs it.

7.4 SSH from Termux

pkg update && pkg upgrade
pkg install openssh
ssh <user>@10.8.0.1          # WireGuard switched on in the phone first

7.5 Switch SSH to keys, in this order

The SSH journal for the last 15 days shows two logins, and both of them used a password: one arrived over WireGuard and the other from the home Wi-Fi. Switching passwords off first would therefore have locked the phone out, and the key must accordingly be installed and tested before anything else changes.

# 1. In Termux: make a key and install it on the Pi
ssh-keygen -t ed25519 -C "phone-termux"
cat ~/.ssh/id_ed25519.pub | ssh <user>@10.8.0.1 'cat >> ~/.ssh/authorized_keys'
ssh <user>@10.8.0.1          # must log in WITHOUT the account password

# 2. On the Pi, with that session still open: switch passwords off
echo 'PasswordAuthentication no' | sudo tee /etc/ssh/sshd_config.d/10-keys-only.conf
sudo sshd -t && sudo systemctl reload ssh
sudo sshd -T | grep -i passwordauthentication     # expect: passwordauthentication no

It should be noted that the name of the drop-in file matters. On this Pi, 50-cloud-init.conf already sets PasswordAuthentication yes, and because sshd keeps the first value it reads while drop-ins load in name order, a file named after it would be silently ignored; the change was therefore made in 10-keys-only.conf on 8 November, confirmed with sudo sshd -T, and a password-only login was then refused. A new Termux session should then log in successfully before the old session is closed, and port 22 should never be forwarded on the router. Interestingly, the journal records no failed password attempts in 15 days, which suggests that port 22 is not reachable from the internet, since an exposed SSH port usually attracts guessing within hours.

Step 8: Backups and updates

Backups work as intended. A cron job runs scripts/backup.sh at 03:00 every night; it copies the live database, the uploads, the images, an encrypted copy of .env and the tunnel configuration, and then pushes them to a private GitHub repository. The most recent run, at 03:00 on 8 November, completed at 109 MB.

A restore, on the other hand, has never been rehearsed. A restore.sh script exists, yet a backup that has never been restored remains an assumption rather than a safeguard; the rehearsal should therefore restore into a throwaway container on another port, confirm that /api/products returns the products, and then delete the throwaway.

Updates, by contrast, are broken. A weekly job runs the following script as the ordinary user every Sunday at 02:00:

#!/bin/bash
apt update
apt full-upgrade -y
apt autoremove -y

cd ~
docker compose pull
docker compose up -d
docker image prune -af
docker volume prune -f

The Docker half of the script works, whereas the apt half has failed with "permission denied" on every one of its 25 weekly runs since May, because apt requires root. As a result the last full upgrade on record dates from 27 January 2026. In other words, the job runs every week while the system it was written to update falls further behind. The failure even concealed its own size: package lists last refreshed on 31 October showed 40 updates waiting, 13 of them for security, whereas freshly refreshed lists showed 56 and 29. The 29 security updates were therefore installed by hand on 8 November, after a database backup, and no container restarted.

The lasting fix was applied on 8 November: Debian's unattended-upgrades package now installs updates every morning through the system's own timers, running as root. It should be noted, however, that a filter for Debian security alone would have missed two important libraries on this Pi, because Raspberry Pi OS rebuilds libc6 and OpenSSL (libssl3t64) and ships their fixes from its own repository. The configuration therefore admits that repository as well, whereas it blocks kernel, firmware and boot packages, since those need a reboot and remain a manual task:

sudo apt install unattended-upgrades
sudo unattended-upgrade --dry-run --debug     # check what the first run would do

// /etc/apt/apt.conf.d/20auto-upgrades
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";

// /etc/apt/apt.conf.d/52unattended-upgrades-local
// Debian security, plus the Raspberry Pi repository, which rebuilds libc6 and
// libssl3t64 (OpenSSL) and ships their fixes. Debian point releases, Docker and
// NordVPN are NOT included. Kernel, firmware and boot packages are blocked: they
// need a reboot and are done by hand. Never reboots by itself.
#clear Unattended-Upgrade::Origins-Pattern;
Unattended-Upgrade::Origins-Pattern {
        "origin=Debian,codename=${distro_codename},label=Debian-Security";
        "origin=Debian,codename=${distro_codename}-security,label=Debian-Security";
        "origin=Raspberry Pi Foundation,codename=${distro_codename}";
};
Unattended-Upgrade::Package-Blacklist {
        "linux-image-";
        "linux-headers-";
        "linux-kbuild-";
        "raspi-firmware";
        "rpi-eeprom";
        "firmware-";
        "initramfs-tools";
};
Unattended-Upgrade::Automatic-Reboot "false";
Unattended-Upgrade::Remove-Unused-Dependencies "false";

A dry run listed 15 packages for the first automatic run, namely the browsers, a code editor and the graphics libraries, and none of them restarts Docker, SSH or systemd. The run also held back the newer 6.18 kernel, as intended, because a package that depends on a blocked kernel package is skipped rather than forced. Finally, the three apt lines were removed from the weekly job, whose Docker half continues unchanged, and the installer's log is kept in /var/log/unattended-upgrades/ for the next check.

Rules worth keeping

Taken together, the steps above suggest ten rules worth keeping.

  1. Visitors should reach Cloudflare and never the house, which means publishing the site through an outbound tunnel rather than through a forwarded port.
  2. The configuration to edit is the one the service actually reads, as systemctl cat <unit> shows, rather than the copy kept in the home folder.
  3. Each project deserves a tunnel of its own, so that one project's mistake cannot take another project offline.
  4. Real secrets belong at runtime and never in build arguments, where docker history exposes them to anyone who holds the image.
  5. The container should run migrate deploy on every start and seed the database exactly once.
  6. Anything that only the tunnel needs should be bound to 127.0.0.1 rather than to every network interface.
  7. A data endpoint should be checked after every deploy, since /api/health alone can stay green while the shop is broken.
  8. The phone's key must be installed and tested before passwords are switched off, or the phone loses its only way in.
  9. A job that runs is not necessarily a job that works, and its log is therefore the only reliable evidence of what it did.
  10. Automatic renewal should be switched on for the domain, because an expired name takes the site offline without warning.

Summary and conclusion

This guide set out to record, step by step, how a Next.js shop is packaged with Docker, published through a Cloudflare Tunnel and administered from a phone over WireGuard and Termux. The setup works: the site is served through Cloudflare's edge, the home address stays out of public DNS, anonymous writes are refused, and the database is backed up every night to a private repository.

This guide does not claim, however, that the setup is complete. Rather, it shows that two of the risks found while writing it have since been fixed, namely an operating system that went unpatched from January until 8 November and an SSH server that accepted passwords, whereas three remain: a tunnel program that never updates; a phone profile that depends on a home address which can change without notice; and the absence of any external check on availability. In addition, the shop runs on one Pi, one drive, one power supply and one broadband line; the router and the phone were not inspected directly; a second WireGuard peer has not connected since the Pi last started; and the install routes for Docker, cloudflared and the WireGuard keys were not recorded, so the standard documented routes are shown in their place. Everything marked as not yet applied therefore remains untested on this Pi.

It should be noted, finally, that five of the first readings taken while writing this guide were wrong: a 30-day log that held only 15 days, a memory figure of zero, a DNS dependency that did not exist, a claim of no open ports that WireGuard disproved, and an admin-route test that reached a page which did not exist. The same discipline therefore applies here as in testing AI output, namely that the first answer is a hypothesis until the running system confirms it.
